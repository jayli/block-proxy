# 已替代：客户端预连接池鲁棒性设计

> 此设计采用“始终维持 3 条健康连接”的策略，已被更小的 tombstone 方案替代。
> 请改用 `docs/plans/2026-08-16-client-tls-preconnect-tombstone-design.md`。

**日期：** 2026-08-15  
**状态：** 待审阅  
**范围：** `client/proxy_core.py` 的 `UpstreamPool`，同时覆盖 SOCKS5-over-TLS 与 HTTP 上游模式

## 1. 目标与边界

客户端预连接池维持 3 条只完成 TCP/TLS 建连、尚未执行 SOCKS5 或 HTTP CONNECT
握手的空闲连接。真实请求优先借用其中一条；被借用的连接随即脱离池，并继续由现有
握手和中继逻辑管理。

本次改动的目标是：

1. 服务端主动关闭空闲预连接后，客户端在下一次巡检时发现并移除失效连接，随后补足
   至 3 条。
2. 真实请求消费池中连接后，立即触发补位，而不是被动等待下一次普通巡检。
3. 连接失败、并发消费、客户端停止时不产生重复补建、socket 泄漏、FD 泄漏或遗留后台
   任务。
4. SOCKS5-over-TLS 与 HTTP plain-TCP 共享同一套池生命周期；两者后续握手语义保持不变。

本次明确不做：

- 不改任何服务端代码、配置或日志；服务端等待首个 SOCKS5 greeting 的 15 秒超时保持
  原样。
- 不引入服务端预连接上限、容量通知、客户端退避协议或 SOCKS 私有扩展。
- 不把 SOCKS5 greeting、认证或 HTTP CONNECT 提前放入预连接阶段。
- 不新增用户可配配置项，也不改变 `POOL_SIZE = 3` 和 `POOL_CHECK_INTERVAL = 1.0`。

## 2. 当前问题

当前 `UpstreamPool` 用 `asyncio.Queue.qsize()` 判断池是否已满。服务端关闭一条空闲 TLS
预连接后，客户端队列仍然保留该 `(reader, writer)`，因此 `qsize()` 仍是 3，维护协程
不会补建。只有真实请求调用 `acquire()` 时，才通过 `writer.is_closing()` 或
`reader.at_eof()` 丢弃失效项并现场新建连接。

这会让预连接池在服务端回收后长时间“表面满、实际失效”，降低真实请求命中预连接的
概率。

## 3. 架构

### 3.1 受管 idle 集合

`UpstreamPool` 改为维护显式的 idle 连接集合，而不是把 `asyncio.Queue` 的长度当作连接
健康度。集合中只存储当前属于池且可供借用的 `(reader, writer)`；目标容量恒为 3。

连接拥有者唯一且明确：

| 状态 | 拥有者 | 关闭责任 |
| --- | --- | --- |
| `idle` | `UpstreamPool` | 池巡检或 `stop()` |
| `borrowed` | 现有真实 SOCKS/HTTP 请求流程 | 现有握手失败和中继清理路径 |
| `candidate` | 唯一补建协程 | 入池失败、停止或取消时由补建协程关闭 |

`borrowed` 连接绝不重新放回预连接池。这样避免把已发送协议字节、已认证或正在传输数据
的连接误当作空闲预连接。

### 3.2 借用与补位

`acquire()` 从 idle 集合原子移出一条连接：

1. 若该连接仍健康（`!writer.is_closing()` 且 `!reader.at_eof()`），立刻发出补位信号后
   返回它。
2. 若该连接已经失效，先将其移出池并关闭，然后继续寻找下一条。
3. 若 idle 集合为空，保留当前语义：现场调用 `create_connection()`，不等待池恢复，保证
   用户请求不因预连接维护而被阻塞。

借用或移除连接只唤醒补建协程，不会为每个调用创建新的补建 task。

### 3.3 巡检与串行补建

池启动时创建一个唯一的维护协程。它由补位信号立即唤醒，同时以当前 1 秒间隔巡检，
以便发现服务端关闭的 idle 连接。

每轮维护执行以下动作：

1. 从 idle 集合移除 `reader.at_eof()` 或 `writer.is_closing()` 的条目；条目先脱离集合，
   再走已有 `_close_writer()`。
2. 若当前 idle 数量小于 3，串行调用 `create_connection()` 直至补足或本轮建连失败。
3. 建连成功的候选连接仅在池仍运行且仍有空位时入池；否则立即关闭。

整个池只有这一个协程负责后台补建，因而多条请求同时借用、多个失效连接同时被发现时，
不会造成连接风暴或超过 3 条 idle 连接。

不使用后台 `reader.read()` 监听关闭。后台读取会与真实 SOCKS5/HTTP 握手争夺输入字节；
巡检只读取 asyncio 已暴露的 EOF/closing 状态，不消费应用协议数据。

## 4. 失败、停止与日志规则

- **建连失败：** idle 池保持缺口，记录现有风格的 debug 日志，下一次 1 秒巡检再尝试；
  不忙等、不启动并发重试。
- **借用后握手失败：** 保持 `_connect_with_pool()` 的既有兜底：关闭借出的连接后，现场
  新建连接并重试一次真实握手。后台池仍自行补回预连接缺口。
- **服务端自然回收：** EOF 被巡检发现后，客户端只记录 debug 信息；它是当前 15 秒服务端
  策略下的正常现象，不应产生 warning/error 噪音。
- **停止竞争：** `stop()` 先禁止新的补建、取消并等待维护协程退出，再关闭 idle 集合内
  所有连接。维护协程在 `create_connection()` 完成后也必须重新检查运行状态；若停止已
  开始，候选连接不入池而立即关闭。
- **幂等关闭：** 任何路径都必须先从 idle 集合删除，再关闭 writer。这样一条 idle 连接
  最多由池关闭一次。

## 5. 15 秒服务端超时的运行影响

本设计有意保持服务端现有 15 秒等待 SOCKS5 greeting 的行为。因此没有流量时，稳定维持
3 条 idle 预连接意味着：服务器约每 15 秒回收这 3 条连接，客户端在最多约 1 秒后重新
补齐。

这对应每客户端约 12 次/分钟的正常空闲预连接建连；它提升池的可用性，但不会减少服务端
超时次数，也不会把预连接的有效窗口扩展到 15 秒之外。未来若把服务端超时调为 60 秒，
同一客户端机制无需改变，轮换率自然降至约 3 次/分钟。

## 6. TDD 验收

先在 `client/tests/` 为 `UpstreamPool` 添加可控异步单元测试；使用假 reader、writer 和
建连函数，避免依赖真实 15 秒等待。测试要求：

1. `start()` 补足 3 条 idle 连接。
2. 模拟一条连接 EOF 后，巡检将其本地关闭一次并补回一条。
3. 借用健康连接会即时请求补位；借出的连接不受 `stop()` 影响。
4. 借到刚失效的连接时，调用方仍可走既有现场建连兜底。
5. 多个并发借用或重复补位信号下，后台最多只有一个补建协程，idle 数量不超过 3。
6. 连续建连失败以巡检间隔重试，不产生忙等或额外 task。
7. `stop()` 与补建进行中竞争时，idle 和未入池 candidate 全部关闭，维护 task 退出。
8. SOCKS5 TLS 与 HTTP plain-TCP 两种配置继续使用各自正确的建连参数和既有后续握手。
9. 多轮 EOF、补位、停止压力测试后，每个测试创建的 writer 要么已借出，要么已关闭一次，
   不遗留 idle writer 或维护 task。

实现阶段严格执行 Red → Green → Refactor，并在完成后运行：

```bash
cd client && pytest tests/
```

## 7. 成功标准

- 服务端关闭 idle 预连接后，客户端最长一个巡检周期发现并补位。
- 真实请求消费连接后，池自动恢复至 3 条，不影响该请求继续握手和传输。
- 客户端停止后没有由池拥有的存活 writer 或遗留维护 task。
- 原有 SOCKS5/HTTP 上游连接和现场建连回退测试全部通过。
