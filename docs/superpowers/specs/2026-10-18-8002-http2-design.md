# 8002 公网代理端口 HTTP/2 复用设计

日期：2026-10-18
状态：待评审

## 1. 背景与目标

8002 端口是面向公网的代理端口（TLS 终结在本机），目前同一端口按首字节分发两种协议：
`0x05` → SOCKS5，ASCII 方法名 → HTTP/1.1 `CONNECT`。两种协议都是「一条 TLS 连接承载一条隧道」，
客户端 `UpstreamPool` 虽然预连 3 条 TLS 套接字，但每条套接字只服务一次握手，之后整条连接被隧道独占，
因此**没有任何连接复用**。每次新 TCP 连接都要重新付出 TLS 握手（1~2 RTT）与 TCP 慢启动成本。

目标：

1. 8002 支持 HTTP/2 CONNECT 多路复用：一条 TLS 连接上并发承载多条隧道。
2. 客户端与服务端**都支持 h2 时使用 h2**；客户端不支持（或无 ALPN）时服务端行为完全不变；
   服务端不支持时客户端自动降级为 HTTP/1.1，且本代配置内不再重试。
3. 现有 SOCKS5 / HTTP/1.1 路径、认证语义、下游 8001 转发、拦截与 MITM 能力**保持不变**。
4. 顺带让 8002 可被 `curl --proxy-http2` 等标准 h2 客户端使用。

非目标（本次不做）：

- Android / iOS 客户端（Android 只走 8003 隧道，不涉及 8002；iOS 源码不在本仓库）。
- 8001 内网代理、8003 隧道、h2c 明文升级（`socks5_tls="0"` 时保持现状，不启用 h2）。
- 新增配置项、后台 UI、命令行开关。
- h2 会话的最长存活时间上限（恶意长连接与现有 8001 keep-alive 属同一风险面，本次不引入新机制）。

## 2. 现状与约束（已核对代码）

- `socks5/server.js#init()`：`enableTls` 时 `tls.createServer(tlsOptions, protectedConnectionHandler)`，
  否则 `net.createServer(...)`；`createPublicProxyHandler()` 读取首包后按 `chunk[0]` 分发。
- `createHttpConnectHandler()`：解析请求行 → 校验 `CONNECT` → `parseConnectTarget()` →
  Basic 认证（主凭据 + 临时凭据，失败回 407 并 `attacker.countIPAccess`）→ 200 并发上限 →
  连 `127.0.0.1:8001` 发 `CONNECT`，2xx 后回 `HTTP/1.1 200 Connection Established` 并双向 pipe。
  该 handler 对客户端 socket 设 120s idle 超时。
- 认证语义：`auth_username` 为空则不校验；命中 `temp_credentials.json` 亦可；
  `proxy-authorization` 必须剥离后再转发给 8001（8001 对 127.0.0.1 来源免认证）。
- 客户端 `client/proxy_core.py`：`_build_ssl_context()` 生成 `_ssl_ctx`（`allowInsecure` 时关校验）；
  `open_node_connection()`（`client/node_connect.py`）负责 DoH 解析、多 IP 尝试、SNI 被拦截时降级；
  `_connect_upstream()` 对 `protocol == "http"` 调 `connect_upstream_http()` 或 `UpstreamPool` 预连套接字；
  `relay()` 依赖 writer 的 `write / drain / can_write_eof / write_eof / close / wait_closed / is_closing`
  与 `writer.transport.get_write_buffer_size()`、`writer.transport.get_extra_info("socket")`、`writer.transport.abort()`。
- 客户端打包：`client/build.sh` 用 Nuitka `--standalone`，并逐个 `--include-data-files` 列出顶层 .py
  （编译后窗口子进程用系统 Python 读同级源码）；`client/tests/test_build_script.py` 强制校验该清单。
- 本地已用一次性探针验证（Node 26 + hyper-h2 4.3）：`tls.createServer({ALPNProtocols:['h2','http/1.1']})`
  把解密后的 TLSSocket 交给 `http2.createServer().emit('connection', socket)`，服务端 `stream` 事件能收到
  `CONNECT`；Python 侧一条 TLS 连接 3 条 CONNECT 流并发、70KB 双向回显与流控均正常。
  该「同端口双栈」手法与 npm 包 `httpolyglot` 一致（Node ≥ 8 通用）。

## 3. 协议与协商

### 3.1 ALPN

服务端 TLS 选项新增 `ALPNProtocols: ['h2', 'http/1.1']`（`socks5_tls="1"` 时）。协商矩阵：

| 客户端 ALPN | 服务端结果 | 服务端行为 |
| --- | --- | --- |
| `['h2', 'http/1.1']` / `['h2']` | `h2` | 进入 HTTP/2 CONNECT 处理 |
| `['http/1.1']` | `http/1.1` | 现有首字节分发（HTTP/1.1 CONNECT 路径） |
| 不发送 ALPN（老客户端、xray 等） | `false` | 现有首字节分发（SOCKS5 / HTTP/1.1 都照旧） |

客户端侧：

| 服务端情况 | 客户端结果 |
| --- | --- |
| 新服务端 | 选中 `h2`，走复用池 |
| 老服务端（无 ALPN 支持） | `selected_alpn_protocol()` 为 `None` → 关闭该连接、标记降级、改走现有 HTTP/1.1 路径（本次多付一次握手，本代配置内不再尝试） |
| 未启用 TLS（`tls=false`） | 不启用 h2，完全保持现状 |

降级是**单向 sticky**：一旦某个配置代际内判定服务端不支持 h2，后续所有连接走原路径；
客户端重启或配置变更（新的 `ProxyCore.start()`）重新协商。

### 3.2 CONNECT 流

请求（HEADERS，END_STREAM=0）：

```
:method: CONNECT
:authority: <host>:<port>        # IPv6 用 [addr]:port，缺省端口 443（与 parseConnectTarget 一致）
proxy-authorization: Basic ...   # 仅配置了凭据时携带
```

规则：CONNECT 请求**不得**携带 `:scheme`、`:path`（RFC 9113 §8.5；探针确认 Node 会以
`RST_STREAM(PROTOCOL_ERROR)` 拒绝带这两个伪头的 CONNECT）。hyper-h2 出站校验默认强制要求
`:path`/`:scheme`，因此客户端必须以 `H2Configuration(validate_outbound_headers=False)` 构造连接。

响应：`:status` 数字。`200` 之后该流即为隧道，双向 DATA 帧承载字节流；`END_STREAM` 表示单向关闭（半关闭）。

状态码映射：

| 场景 | 响应 |
| --- | --- |
| 下游 8001 返回 2xx | `200` |
| 下游返回非 2xx | 透传数字状态码（407 时一并透传 `proxy-authenticate`） |
| `:authority` 无法解析 | `400` |
| 非 `CONNECT` 方法 | `501` |
| 缺少/错误凭据（含临时凭据不匹配） | `407` + `proxy-authenticate: Basic realm="BlockProxy"` |
| 超过并发隧道上限 | `503` |
| 连接下游失败 | `502` |

### 3.3 流控

- 客户端通告 `INITIAL_WINDOW_SIZE = 262144`（256 KiB/流）、`ENABLE_PUSH = 0`；
  每把已交付给上层的字节数用于 `WINDOW_UPDATE`，即**按消费量确认**，读取慢的上层最多积压一个窗口
  （200 流全部停滞的上限约 50 MB，仅在该病态场景出现）。
- 发送侧按 `min(local_flow_control_window, max_outbound_frame_size)` 切片，窗口不足时缓存并在
  收到 `WINDOW_UPDATE` 后继续；缓存上限由 `relay()` 现有的 `get_write_buffer_size() > 65536` 触发 `drain()` 约束。
- 服务端使用 Node 的 `stream.pipe(upstreamSocket)` / `upstreamSocket.pipe(stream)`，背压与窗口更新由 Node 处理。

## 4. 服务端设计（`socks5/server.js`）

### 4.1 新增函数

```js
createHttp2ConnectHandler(options) -> http2.Http2Server
createPublicProxyDispatcher(options) -> { handleConnection(socket), h2Server, close() }
```

- `createHttp2ConnectHandler`：
  - `http2.createServer({ settings: { maxConcurrentStreams: options.maxTcpConnects ?? 200 } })`。
  - 复用 `options.authCredentials`、`options.attacker`、`options.maxTcpConnects`、`options.logger`，
    与 `createHttpConnectHandler` 同名同义，便于测试注入。
  - `stream` 事件：
    1. 取 `headers[':method']`；非 `CONNECT` → `501` 并 `end()`。
    2. `parseConnectTarget(headers[':authority'])` 失败 → `400`。
    3. IP 黑名单（`attacker.isBadGuy`）→ `407` + `session.close()`；凭据校验失败（主凭据与
       `tempCredentials` 均不匹配）→ `attacker.countIPAccess` + `407`；成功 → `setGoodGuy`。
    4. 全局 `activeTunnels >= maxTcpConnects` → `503`。
    5. `net.connect(127.0.0.1, proxy_port)` → 写 `CONNECT host:port HTTP/1.1\r\nHost: ...\r\n\r\n`
       （不携带 `proxy-authorization`）→ 读到响应头：2xx → `stream.respond({':status': 200})` 并双向 pipe；
       非 2xx → `stream.respond({':status': <code>})` 并 `end()`。
    6. 清理：`stream`/`proxySocket` 的 `error`、`close` 均幂等减计数并互相关闭；不设置 socket idle 超时。
  - 会话级：`session` 事件记录 `activeSessions`；`sessionError`/`error` 只记日志；
    不对 h2 会话设置 120s idle 超时（那是单条 1.1 隧道的策略）。
  - 日志：`[H2] session open remote=<ip> sessions=<n>`、隧道建立失败/超限警告、会话关闭。
- `createPublicProxyDispatcher`：把现有 `createPublicProxyHandler` 的分发主体收进来：

```js
function handleConnection(socket) {
  if (h2Server && socket.alpnProtocol === 'h2') {
    h2Server.emit('connection', socket);   // 解密后的 TLSSocket 直接交给 http2 解析
    return;
  }
  // 原逻辑原样：读首包 → 0x05 走 SOCKS5，否则 HTTP/1.1 CONNECT
}
```

`net.createServer` 场景下 `socket.alpnProtocol` 为 `undefined`，恒走原逻辑。

### 4.2 `init()` 改动

- TLS 选项加 `ALPNProtocols: ['h2', 'http/1.1']`（仅 `enableTls` 时）。
- 用 `createPublicProxyDispatcher()` 替代 `createPublicProxyHandler()` 作为连接处理函数。
- 启动日志补一行 h2 状态（`ALPN h2 复用已启用`）。
- 纯 TCP 模式不加 ALPN、不启用 h2。

### 4.3 保持不变

SOCKS5 处理、HTTP/1.1 CONNECT 处理、TLS 证书与 ticket-keys、`attacker` 限频状态、临时凭据、
`enable_socks5`/`socks5_tls` 配置、`_test` 导出（新增 h2 相关工厂，不改已有签名）。

## 5. 客户端设计（`client/h2_upstream.py` + `client/proxy_core.py`）

### 5.1 新模块 `client/h2_upstream.py`

只依赖标准库 + `h2`（hyper-h2，纯 Python）。

```python
class H2UpstreamPool:
    def __init__(self, server_config, ssl_ctx, *, verify_cert_pin=None,
                 logger=logger, max_sessions=2, streams_per_session=50)
    async def start(self)          # 维护任务：预热/修剪会话，失败退避重试，不抛
    async def stop(self)           # 关闭全部会话（GOAWAY + 关闭 socket）
    async def connect(self, host, port) -> (reader, writer) | None
    @property
    def disabled(self) -> bool     # 降级标记（本代配置内不再尝试 h2）
```

- `connect()`：
  - `disabled` → 返回 `None`。
  - 选负载最小（活动流最少）且未 draining 的会话；无可用会话（或已达 `streams_per_session`
    且会话数 < `max_sessions`）→ 新建会话。
  - 分配流 id，写 HEADERS（见 3.2），等 `ResponseReceived`（超时 `HANDSHAKE_TIMEOUT = 10`）；
    `:status == 200` → 返回 `(H2StreamReader, H2StreamWriter)`；否则关闭该流并抛
    `Exception("HTTP proxy CONNECT failed: <status>")`（与现有 1.1 路径的错误文案风格一致，便于日志对照）。
  - 建会话时若 `selected_alpn_protocol() != 'h2'`：关闭连接、置 `disabled = True`、返回 `None`
    （调用方块降级到原路径，只浪费这一次握手）。
  - 建会话流程复用 `open_node_connection()`（DoH 解析、多 IP、SNI 回退）→ 证书 pin（传入非空时）
    → `H2Connection(H2Configuration(client_side=True, header_encoding='utf-8', validate_outbound_headers=False))`
    → `initiate_connection()` + `update_settings({INITIAL_WINDOW_SIZE: 262144, ENABLE_PUSH: 0})` → 启动 pump。
- 会话生命周期：
  - pump 协程唯一消费 TLS 流，事件分派到各流的 reader/writer / 窗口事件 / PING ack / GOAWAY。
  - 空闲 60s 发 PING（无业务流时），10s 内无 ACK 判死；有流在跑不发 PING（有流量即活）。
  - 无活动流超过 10 分钟关闭会话（下次用时再建）；`max_sessions=2` 时的多余空闲会话先关。
  - 收到 GOAWAY：标记 draining，不再接新流，已有流继续；新流走新会话。
  - 会话死亡：其上所有流 reader 置 EOF/异常、writer 关闭（本地连接随之关闭），下一次 `connect()` 自动重连。
- 流级垫片（与 `relay()` 的既有契约对齐）：
  - `H2StreamReader`：`async read(n)`（返回 `b''` 表示 EOF）、`at_eof()`；按消费量回 `WINDOW_UPDATE`。
  - `H2StreamWriter`：`write()`（同步尽力发送 + 余量入缓冲）、`async drain()`（等窗口）、`close()`、
    `is_closing()`、`can_write_eof() -> True`、`write_eof()`（发 `END_STREAM`，实现真正半关闭）、`wait_closed()`；
    `transport` 为垫片对象：`get_write_buffer_size()`（缓冲字节数）、`get_extra_info(_)` 返回 `None`
    （使 `_set_nodelay` / `SO_LINGER` 自动跳过，避免影响共享连接）、`abort()` 只对**本流**发
    `RST_STREAM(CANCEL)`，绝不 abort 共享 TLS 连接。

### 5.2 `client/proxy_core.py` 接入

- `_build_ssl_context()`：`protocol == "http"` 且 `tls` 时额外构造 `self._h2_ssl_ctx`
  （同样的 `check_hostname`/`verify_mode`，再加 `set_alpn_protocols(['h2','http/1.1'])`）。
  `_ssl_ctx` 本身**不改**，因此健康检查、延迟测量、SOCKS5 路径都不会被协商成 h2。
- `_start_local_proxy()`：`protocol == "http"` 且 `tls` → 创建并 `start()` `H2UpstreamPool`；
  原 `UpstreamPool` 仍创建但**不 start**（避免 h2 生效时空占 3 条 TLS 套接字）。
- `_connect_upstream()`（http 分支）：
  ```python
  if self._h2_pool is not None and not self._h2_pool.disabled:
      pair = await self._h2_pool.connect(host, port)
      if pair is not None:
          return pair
      await self._upstream_pool.start()      # 降级：此时才启动旧池
  ```
- `_stop_local_proxy()`：先 `await h2_pool.stop()` 再停旧池，保持「先关 listen socket、再 await」
  的既有顺序约定；`_start_local_proxy()` 顶部把 `_h2_pool` 置 `None`，与 `_upstream_pool` 同样处理。
- 异常语义：h2 会话建不起来（网络/证书 pin 失败等）与今天 `open_node_connection()` 失败一样上抛，
  由 `_do_handle_socks` / `_do_handle_http` 记录并关闭本地连接，不做隐式双连接重试。
- 日志：首次进入 h2 记一条 `HTTP/2 复用已启用（ALPN h2）`；降级时记一条
  `服务端未协商 h2，回退 HTTP/1.1`（每次 `start()` 至多一条）。

## 6. 兼容性与风险

| 项 | 结论 |
| --- | --- |
| 老客户端（无 ALPN）连新服务端 | 服务端 `alpnProtocol === false`，首字节分发，行为零变化 |
| 新客户端连老服务端 | 首次连接未协商到 h2 → 降级，本代配置内走原路径，功能不变 |
| SOCKS5 客户端 | 不发送 ALPN，路径完全不变 |
| 已装证书 / 证书 pin (TOFU) | 建 h2 会话后按现有 `_verify_cert_pin` 校验，失败即报 `CertPinMismatchError` |
| 认证 / 临时凭据 / IP 限频 | 语义与 1.1 路径一致（同一 `attacker` 状态，同一凭据来源） |
| 拦截、MITM、访问日志 | 下游仍是 8001 的 `CONNECT`，不受影响 |
| TCP 层 HOL 阻塞 | 默认 2 条会话分散负载（单会话软上限 50 流）；代价是 2 个 fd 与 2 次 TLS |
| 单会话死亡爆炸半径 | 仅影响该会话上的流，本地连接被关闭、应用重试；下一次 `connect()` 自动重建 |
| 内存 | 按消费量确认窗口，最多约 1 个 256 KiB 窗口/流 |
| Node 版本 | 手法与 `httpolyglot` 一致（Node ≥ 8）；本地 Node 26 已验证，需在仓库 Node 版本下跑测试确认 |
| EDR / 安全软件 | 客户端新增的是纯 Python 依赖，无新二进制特征 |

## 7. 测试计划

### 7.1 服务端（新增 `test/public-proxy-h2-tests.js`，并入 `npm run test:public-proxy`）

假下游 8001 沿用现有 echo 模式（`test/public-proxy-protocol-tests.js` 的小工具抽到可共享位置或各自复制一份）。

1. TLS + ALPN `h2` → 单连接两条 `CONNECT` 流同时 echo，互不串包（复用核心断言）。
2. 同连接 1 MB 双向回显（流控与 `WINDOW_UPDATE`）。
3. 无凭据配置时任意客户端可连；配置凭据后：正确凭据 200、缺失/错误 407 且 attacker 计数、
   临时凭据可过、`proxy-authorization` 不出现在下游请求头。
4. 非 `CONNECT` 方法 → 501；非法 `:authority` → 400；超过 `maxTcpConnects` → 503。
5. 下游 502 → 透传 502 并结束流。
6. 回归：ALPN `http/1.1` → 现有 HTTP/1.1 CONNECT 正常；**完全不发 ALPN** → SOCKS5 握手正常。
7. 同一 TLS 端口上 SOCKS5（无 ALPN）与 h2（ALPN h2）互不影响。

### 7.2 客户端（新增 `client/tests/test_h2_upstream.py`）

用 Python 侧的 h2「假服务端」（同样 `validate_outbound_headers=False`，按 3.2 回 200 后 echo）：
1. 两条隧道复用**同一条** TLS 连接（服务端统计连接数 == 1），双向并发 echo 正确。
2. 服务端 ALPN 仅 `http/1.1` → `connect()` 返回 `None`、`disabled` 置位、不抛异常。
3. 双向大包（> 单窗口）流控正确、无死锁。
4. `RST_STREAM` / 会话断开 → reader 收 EOF 或异常、writer `wait_closed()` 正常返回，无未捕获异常。
5. `write_eof()` 发 `END_STREAM`（服务端读到半关闭，仍可回写）。
6. 垫片契约：`can_write_eof()`、`transport.get_write_buffer_size()`、`transport.abort()` 只重置本流。
7. `relay()` 真实跑通（本地 echo 套接字 ⇄ h2 流）。
8. 会话重建：会话断开后下一次 `connect()` 建立新连接（服务端连接计数 +1）。

### 7.3 端到端与回归

- `npm run test:public-proxy`、`npm run test:proxy-core`（不回归）。
- `cd client && python3 -m pytest tests/ -q` 全量。
- 手动端到端：用导出的服务端工厂 + 真实 `cert/socks5_tls.*` + 假 8001 起一个 8002；
  用真实客户端代码（`protocol=http`、`tls=true`）跑 2 并发隧道 + 1 MB 传输，确认只建 1 条 TLS 连接；
  再用 `curl --proxy https://127.0.0.1:<port> --proxy-http2 --proxy-insecure` 走一遍第三方客户端。
